# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ

## 1.2 Аналіз існуючих аналогів

Для інженерного порівняння обрано OldSkool ProMod, WOTInspector і Freemius. ProMod розглянуто як тематичний аналог інфраструктури розповсюдження ігрового freemium-продукту; WOTInspector — як аналог керування доступом до ігрових інструментів та оброблення статистичних даних; Freemius — як функціональний аналог платформи ліцензування й супроводу цифрового програмного продукту. Повного збігу предметних областей не передбачено: кваліфікаційний проєкт охоплює інфраструктуру одного готового продукту, а не розроблення ігрового помічника, модифікацій або універсального платіжного сервісу.

Аналіз виконано за офіційними джерелами, доступними станом на 08.10.2026. Відокремлено документовані властивості від інженерних висновків про залежності та обмеження. Відомості про непублічні компоненти позначено як нерозкриті. Числових результатів Latency/RPS, тестування конкурентів або підтверджених вразливостей не отримано; їх не підмінено припущеннями. Опис запропонованої платформи відображає проєктні рішення з ЛР №2, а не результати навантажувальних вимірювань.

### 1.2.1 OldSkool ProMod

**Архітектура та масштабування.** У публічному описі автора наведено клієнтський інсталятор на .NET 8, власні сервери контенту та запуск оновлень перед стартом Wargaming Game Center. Отже, на рівні спостережуваної взаємодії встановлено модель client–server для доставки модифікацій. Поділу серверного застосунку на мікросервіси, кількості вузлів і механізмів горизонтального масштабування не розкрито. Наявність окремого клієнта та контентних серверів не доводить мікросервісної будови backend. [Опис автора у WGMods](https://wgmods.net/535/).

**Протоколи та доступ.** Вебсторінки й точки завантаження доступні через HTTPS. За правилами Premium доступ пов’язано з Wargaming ID та ігровим ім’ям; після його надання передбачено перезапуск гри. Публічного контракту REST API, gRPC, GraphQL або брокера повідомлень для сервісу перевірки Premium у використаних джерелах не виявлено. Протокол між клієнтом оновлень і сервером контенту окремо не специфіковано. [Premium](https://www.oldskool.vip/en/premium/), [розповсюдження](https://www.oldskool.vip/en/download/).

**Дані та консистентність.** За описом автора вибір модифікацій зберігається для кожної інсталяції гри. Це підтверджує локальний стан клієнта, але не визначає серверну СУБД. Тип SQL/NoSQL, транзакційність, реплікація та спосіб узгодження стану Premium між клієнтом і сервером не розкриті. Доступ за Wargaming ID не прирівняно до активації ліцензійним ключем або до контролю апаратних ідентифікаторів пристроїв.

**Інженерні обмеження.** Пакети модифікацій пов’язані з версією гри; у картці автора окремо вказано підтримувану версію та журнал сумісності. З цього випливає потреба узгоджувати реліз клієнтського продукту й доступний пакет. Залежність завантаження від сервера контенту та перевірки ідентичності від зовнішнього провайдера є інженерним висновком про точки відмови, а не повідомленням про фактичний збій. Вебсторінка Premium називає повністю автоматичний updater запланованим, тоді як картка WGMods уже описує автоматичне оновлення для Premium; тому ці описи не використано як єдиний доказ поточної поведінки всіх версій клієнта. Публічних SLA та резервування не наведено. [Premium](https://www.oldskool.vip/en/premium/), [журнал автора](https://wgmods.net/535/).

### 1.2.2 WOTInspector

**Архітектура та масштабування.** Документовано вебсервіси та застосунки для аналізу броні, карт і записів боїв World of Tanks. На зовнішній межі встановлено client–server-взаємодію через версіонований API. Внутрішній патерн backend, сервісну декомпозицію та розподіл обчислень між вузлами не розкрито; окремі вебадреси сервісів не є доказом мікросервісної архітектури. [Документація API](https://api.wotinspector.com/).

**Протоколи та доступ.** Офіційна специфікація OpenAPI 3.0.3 описує HTTP API v2: GET і POST `/v2/replays/`, GET `/v2/replays/{id}/`, `/v2/heatmaps/` та інші ресурси. Для записів боїв визначено JSON-відповіді, пагінацію через `page`, фільтри й завантаження через `multipart/form-data`. Для відповідних операцій наведено `cookieAuth` та `ApiKeyAuth`; схема також містить OAuth2 authorization code flow. Наявність схеми OAuth2 не означає її застосування до кожного endpoint. Обліковий запис використовується для придбаних можливостей, а для Patreon наведено зв’язування з Wargaming ID. [OpenAPI](https://api.wotinspector.com/openapi/), [обліковий доступ](https://wotinspector.com/en/shop/), [Patreon](https://wotinspector.com/en/patreon/).

**Дані та консистентність.** Контрактом описано записи боїв, набори теплових карт, версії ігрових ресурсів і продукти. Наявність JSON у відповіді API не визначає тип сховища. СУБД, транзакційні межі, реплікація та модель консистентності агрегатів не оприлюднені у використаних джерелах. Відомостей про апаратне прив’язування ліцензійних ключів також не отримано. [OpenAPI](https://api.wotinspector.com/openapi/).

**Інженерні обмеження.** Версіоновані пакети ігрових ресурсів і фільтри записів боїв відображають залежність аналізу від платформи та версії даних. В інженерному проєктуванні аналогічної системи потрібно розмежовувати приймання даних, їх агрегування і видачу результатів: це висновок із характеру операцій, а не твердження про наявний bottleneck WOTInspector. Пагінація обмежує розмір окремої відповіді, але не підтверджує певний RPS або горизонтальне масштабування. У магазині наведено різні межі доступу до історії статистики; вони є правилами entitlement, а не доказом браку продуктивності. Retry, резервування, числові rate limits і SLA у розглянутому API не встановлено. [OpenAPI](https://api.wotinspector.com/openapi/), [правила доступу](https://wotinspector.com/en/shop/).

### 1.2.3 Freemius

**Архітектура та масштабування.** Freemius надає зовнішню SaaS-інфраструктуру для ліцензування, підписок, розповсюдження та інтеграції цифрових продуктів. Документовано REST API та передачу подій у backend продукту через webhooks. На межі інтеграції підтверджено поєднання синхронних запитів із подієвою взаємодією; повну сервісну декомпозицію Freemius не розкрито. В описі оновлення від 30.12.2022 документовано окремий аналітичний шар із фоновим індексуванням сирих даних у data warehouses. Це підтверджує розмежування аналітичного оброблення, але не встановлює мікросервісної будови всієї платформи. [Архітектурні зміни аналітики](https://freemius.com/blog/release-notes-real-time-analytics-and-multi-store-dashboard/). [SaaS integration](https://freemius.com/help/documentation/saas/saas-integration/).

**Протоколи та доступ.** Для активації наведено POST `/v1/products/{product_id}/licenses/activate.json` з ліцензійним ключем та `uid` інсталяції. Початкова активація не потребує заголовка Authorization; отриманий `install_api_token` використовується як Bearer token у наступних автентифікованих запитах. `uid` формується клієнтом і сам по собі не доводить апаратного HWID-контролю. Події ліцензій передаються через HTTP POST; для перевірки джерела документовано `x-signature` та HMAC SHA256 за вихідним тілом запиту. [Активація](https://freemius.com/help/api/licenses/activate/), [webhooks](https://freemius.com/help/documentation/saas/events-webhooks/).

**Дані та консистентність.** Через API доступні ліцензії, інсталяції, користувачі й підписки. Для Staged Rollouts документовано записи ліцензованих інсталяцій, таблицю релізів і поля `last_served_update_version`, `limit`, `uniques`, за якими керується поступова видача оновлень. Це характеризує модель даних розповсюдження, але не визначає конкретну СУБД. Основну СУБД, технологію data warehouses, реплікацію та рівні ізоляції транзакцій не названо. [Модель даних Staged Rollouts](https://freemius.com/blog/staged-rollouts-wordpress-plugins-themes/). Для SaaS інтеграції рекомендовано після події отримати актуальний стан через API й оновити entitlement у власній БД; для видаленої ліцензії — прибрати доступ. Така синхронізація створює залежність між двома станами, тому потрібні перевірка повторних подій та звіряння після переривання доставки; це вимоги до інтегратора, а не підтвердження глобальної ACID-транзакції. [Ліцензії](https://freemius.com/help/api/licenses/), [синхронізація SaaS](https://freemius.com/help/documentation/saas/saas-integration/).

**Інженерні обмеження.** Для попередньої реалізації аналітики команда Freemius задокументувала зростання навантаження від прямих запитів до БД, збої dashboard та API timeouts. Перехід до фонового індексування в окремому аналітичному шарі описано як усунення цієї проблеми; її не подано як чинний дефект платформи. [Попередній bottleneck і його усунення](https://freemius.com/blog/release-notes-real-time-analytics-and-multi-store-dashboard/). У документації активації визначено помилки простроченого ключа, вичерпаної квоти та вже активованої інсталяції; остання може сигналізувати про розсинхронізацію клієнта. У журналі від 30.12.2025 задокументовано автоматичне вимкнення webhook listener після понад 100 невдалих доставок і виправлення помилки скидання лічильника відмов. Виправлену помилку не подано як чинну вразливість. Для інтегратора зберігається ризик пропуску змін доступу під час вимкнення listener, тому потрібне відновлення синхронізації. Файли зберігаються в Amazon S3 та видаються через захищений API; це не встановлює стек бази даних або SLA всієї платформи. [Оброблення помилок активації](https://freemius.com/help/api/licenses/activate/), [webhook recovery](https://freemius.com/changelog/improved-webhook-failure-detection-and-recovery/), [розповсюдження файлів](https://freemius.com/help/faq/licensing/).

#### Аналітичний висновок підрозділу

За результатами порівняння встановлено, що в ProMod інфраструктуру орієнтовано на доставку ігрових модифікацій та обліковий Premium-доступ, а у WOTInspector — на API ігрових даних та доступ до аналітичних інструментів. Для запропонованої платформи доцільно використати принцип відокремлення клієнтського продукту від сервера розповсюдження та версіонованих контрактів оброблення статистики. У Freemius документовано керування entitlement через API й події та винесення аналітики в окремий шар після API timeouts від прямих запитів до БД. Для власної платформи враховано принцип відокремлення статистичного оброблення від критичних операцій доступу; реалізація універсального data warehouse не передбачається. Водночас наявність відкритого API або зовнішньої ідентичності не підтверджує підтримки необхідного поєднання Telegram/Discord, збереження формату ключів замовника та правил прив’язування пристроїв. Внутрішні архітектури аналогів не класифіковано як застарілі без доказів.

Для цих вимог обґрунтовано декомпозицію на FastAPI-сервіси з окремими PostgreSQL-сховищами: правила доступу зосереджуються в сервісі ліцензій, а приймання телеметрії та підготовка файлів відокремлюються від обліку користувачів. Реляційні обмеження й локальні транзакції застосовуються для перевірки стану активацій і підписок; RabbitMQ використовується для передавання команд між компонентами, зокрема підготовки платного файлу. Це дає можливість пристосувати контракти та дані до одного готового продукту без перенесення правил доступу в клієнтський інтерфейс або підпорядкування їх універсальній моделі SaaS-провайдера. Перевагу такого стеку визначено відповідністю спеціалізованим вимогам та контролем над станом ліцензій, а не непідтвердженою перевагою Latency/RPS. Вбудоване приймання платежів не передбачається: придбання відбувається через зовнішні канали.

Компромісом обраної архітектури є збільшення кількості процесів, мережевих залежностей і операцій супроводу. Брокер повідомлень не усуває затримок request/reply, повторного виконання команд або втрати узгодженості між окремими БД; контейнеризація не замінює резервування. Тому для проєктування визначено потребу в timeout, кореляції запитів, контролі повторної активації, перевірках доступу перед видачею файлу та відновленні після збоїв. Механізми повторного оброблення й навантажувальні характеристики мають бути підтверджені тестуванням. У Розділі 2 передбачено обґрунтувати межі сервісів, структуру БД, контракти REST/AMQP та послідовності критичних сценаріїв з урахуванням цих обмежень.
