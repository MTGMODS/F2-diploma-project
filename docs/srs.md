# Специфікація вимог до програмного забезпечення (SRS)

**Редакція:** 28.10.2026 · **Статус:** для рев’ю · **Автор:** Маргер Богдан Євгенович, 443А.

Документ застосовує контрактний стиль ISO/IEC/IEEE 29148 і п’ять блоків, установлених ЛР №5. Це навчальна адаптація, а не заява про сертифікацію. Вихідна база — вісім Core Features і десять NFR ЛР №4; їх декомпозовано без підміни цільових метрик результатами тестів. [Базова редакція ЛР №4](https://github.com/MTGMODS/F2-diploma-project/blob/232d6c1b76fb0328305f5f838df761d240585308/docs/1_analysis.md).

## 1. System Context — контекст системи

Платформа повинна забезпечувати інфраструктуру одного готового цифрового freemium-продукту: представлення, розповсюдження, ліцензування та аналітику. Ігрові функції зовнішнього SA-MP-помічника не входять до розроблення. Попередня VIP-система замовника визначає сумісний формат ключів і зв’язування Telegram, Discord або обох ідентичностей.

Актори — відвідувач, користувач і адміністратор. Зовнішні системи — клієнт продукту, Telegram, Discord і канали придбання. Браузер є основним інтерфейсом; Telegram Mini App відкриває той самий вебзастосунок. Telegram Stars обробляє бот; прямий картковий еквайринг на сайті не передбачається.

Межа платформи охоплює React SPA, User/License/Usage/Distribution Services, ботів, три окремі PostgreSQL-БД, RabbitMQ, Redis і файли. HTTPS reverse proxy є інфраструктурою доступу. Міжсервісний HTTP і AMQP працюють у закритому контурі. Доступ до іншої сервісної БД напряму не передбачається. [C4 Levels 1–3](2_design.md) і [ADR-001](adr/0001-choice-of-technology.md) деталізують розподіл відповідальності.

## 2. Functional Requirements — функціональні вимоги

### Публічний вебмодуль — вихідна FR-01

#### SRS-FUN-01
Система повинна показувати опис продукту, інструкції, тарифи й зовнішні способи придбання без входу.

#### SRS-FUN-02
Система повинна надавати безкоштовний інсталятор як статичний файл без персоналізованої збірки.

### User Service — вихідна FR-02

#### SRS-FUN-03
Система повинна автентифікувати користувача через підтримуваний Telegram/Discord-механізм, зокрема Telegram Mini App.

#### SRS-FUN-04
Система повинна зв’язувати одну або обидві соціальні ідентичності з єдиним обліковим записом.

#### SRS-FUN-05
Система повинна видавати підписаний access JWT після успішного входу.

#### SRS-FUN-20
Система повинна видавати refresh-токен для продовження автентифікованої сесії.

#### SRS-FUN-21
Система повинна відкликати попередній refresh-токен під час його ротації.

#### SRS-FUN-22
Система повинна відкликати refresh-токен сесії під час виходу користувача.

### License Service — вихідна FR-03

#### SRS-FUN-06
Система повинна генерувати ключ із 16 символів A–Z/0–9, згрупованих дефісами у форматі `XXXX-XXXX-XXXX-XXXX`; регулярний вираз — `^[A-Z0-9]{4}(?:-[A-Z0-9]{4}){3}$`. Дефіси не входять до 16 значущих символів; повна довжина — 19 символів.

#### SRS-FUN-07
Система повинна переводити ключ зі стану NOT_ACTIVATED у ACTIVE для автентифікованого користувача; відсутній ключ або ключ в іншому стані повинен відхилятися без зміни власника. За наявності іншої активної ліцензії потрібне явне підтвердження заміни (force); без нього повертається 409 ACTIVE_LICENSE_EXISTS.

#### SRS-FUN-08
Система повинна повертати власнику поточний стан його ліцензії у кабінеті.

#### SRS-FUN-24
Система повинна повертати власнику історію його попередніх ліцензій.

#### SRS-FUN-09
Система повинна перевіряти чинність ліцензії під час запиту зовнішнього клієнта продукту.

### Пристрої — вихідна FR-04

#### SRS-FUN-10
Система повинна обліковувати пристрої ліцензії в межах тарифного ліміту.

#### SRS-FUN-11
Система повинна дозволяти власнику скидання власного пристрою в межах доступної квоти.

### Distribution Service — вихідна FR-05

#### SRS-FUN-12
Система повинна повертати тимчасове посилання на персоналізований VIP-файл лише після дозволу License Service.

#### SRS-FUN-13
Після завершення відповіді завантаження Lua система повинна видаляти Lua, пов’язаний EXE, marker `.exe.used` і залишкові персоналізовані EXE цього token. Після відповіді EXE видаляється лише виданий EXE: Lua та marker зберігаються до споживання Lua або sweep, оскільки інсталятор ще звертається до Lua-URL. Після помилки підготовки EXE marker знімається, щоб дозволити повторну спробу. Покинуті файли обробляються за FILE-01/02; шаблони захищені FILE-03.

### Usage Service — вихідна FR-06

#### SRS-FUN-14
Система повинна валідувати й зберігати події запуску зовнішнього продукту.

#### SRS-FUN-15
Система повинна публікувати агрегати використання, трактуючи унікальні HWID як пристрої.

### Придбання — вихідна FR-07

#### SRS-FUN-16
Система повинна обліковувати придбання із зовнішніх каналів і підтверджені Stars-платежі бота.

#### SRS-FUN-17
Система повинна публікувати агрегати продажів із розмежуванням строкових і попередніх lifetime-ліцензій.

### Адміністрування та боти — вихідна FR-08

#### SRS-FUN-18
Система повинна обмежувати адміністративні операції роллю ADMIN.

#### SRS-FUN-19
Система повинна передавати ботам команди припинення VIP-привілеїв після завершення підписки.

#### SRS-FUN-23
Система повинна передавати ботам повідомлення користувачу про завершення підписки.

## 3. Non-Functional Requirements — нефункціональні вимоги

Усі межі є критеріями приймання. API-профілі: Linux, 4 vCPU, 8 GiB RAM, SSD, Docker Compose; генератор працює окремо. Для кожного профілю k6: constant-arrival-rate 50 RPS × 600 с після прогріву, 30000 запланованих запитів. Профіль PERF-01 охоплює публічні usage/sales aggregates; PERF-02 — читання стану/історії власної ліцензії та перевірку ліцензії на контрольованих облікових записах. OAuth, платежі, cold start і передавання файлів виключаються з цих профілів. Час — до повної відповіді клієнту. Відкидання повільних відповідей зі звіту заборонене.

#### SRS-NFR-PERF-01
Публічний API статистики повинен забезпечувати p95 ≤300 мс за вказаного профілю з прогрітим кешем. Джерело: NFR-01.

#### SRS-NFR-PERF-02
Внутрішні операції API повинні забезпечувати p95 ≤500 мс за вказаного профілю. Джерело: NFR-02.

#### SRS-NFR-PERF-03
Кожен визначений API-профіль повинен мати частку помилок ≤1%. Джерело: NFR-01/02.

#### SRS-NFR-PERF-05
Кожен визначений API-профіль повинен мати 0 dropped_iterations із 30000 запланованих запитів. Джерело: NFR-01/02.

#### SRS-NFR-PERF-04
Час отримання VIP-посилання повинен мати p95 ≤30 с на 20 послідовних штатних збірках. Джерело: NFR-03.

#### SRS-NFR-CACHE-01
Кеш агрегатів повинен вважати результат свіжим протягом 300 с після успішного обчислення. Джерело: NFR-04.

#### SRS-NFR-CACHE-03
Кеш агрегатів повинен зберігати результат не довше 86400 с після успішного обчислення. Джерело: NFR-04.

#### SRS-NFR-CACHE-02
Оновлення одного набору кешу повинно виконуватися не більш як одним виконавцем при 20 конкурентних запитах. Джерело: NFR-04.

#### SRS-NFR-CACHE-04
За відсутності кешованого результату конкурентний запит повинен очікувати існуюче оновлення не довше 4 с, після чого отримувати 503 з Retry-After: 2. Джерело: NFR-04.

#### SRS-NFR-SEC-01
Публічний транспорт повинен використовувати TLS ≥1.2. Джерело: NFR-05.

#### SRS-NFR-SEC-02
Система повинна відхиляти access JWT з неправильним підписом, простроченням або типом, відмінним від access. Джерело: NFR-05.

#### SRS-NFR-SEC-05
Система повинна відхиляти повторне використання refresh-токена після його відкликання або ротації. Джерело: NFR-05.

#### SRS-NFR-SEC-03
Система повинна допускати 0 доступів до чужих ліцензій і пристроїв у 100 негативних перевірках. Джерело: NFR-05.

#### SRS-NFR-PRIV-01
Публічні відповіді повинні містити 0 сирих ключів, Telegram/Discord ID і HWID у 100 вибірках. Джерело: NFR-06.

#### SRS-NFR-PRIV-02
Журнали не повинні містити access/refresh-токенів або секретів інтеграцій. Джерело: NFR-06.

#### SRS-NFR-CONS-01
Конкурентна активація повинна давати 0 випадків закріплення одного ключа за різними власниками у 20 спробах. Джерело: NFR-07.

#### SRS-NFR-CONS-02
Конкурентне додавання пристроїв повинно давати 0 перевищень налаштованого ліміту. Джерело: NFR-07.

#### SRS-NFR-REL-01
Очікування file-generation reply повинно завершуватися не пізніше 30 с з відповіддю або контрольованою помилкою. Джерело: NFR-03/08.

#### SRS-NFR-REL-02
Відмова залежностей не повинна дозволяти видачу VIP-посилання для забороненої ліцензії. Джерело: NFR-08. Redis fallback у БД не гарантує PERF-01.

#### SRS-NFR-FILE-01
Фоновий sweep тимчасових файлів повинен запускатися кожні 3600 с. Джерело: NFR-09.

#### SRS-NFR-FILE-02
Sweep повинен видаляти покинуті Lua/EXE/tmp/marker-файли віком >3600 с; за працюючого worker похідна межа віку становить 7200 с плюс тривалість одного sweep. Джерело: NFR-09.

#### SRS-NFR-FILE-03
Очищення тимчасових файлів не повинно видаляти базові Lua/EXE-шаблони. Джерело: NFR-09.

#### SRS-NFR-OPS-01
Стенд повинен відтворювано запускатися через Docker Compose із задокументованою конфігурацією. Джерело: NFR-10.

#### SRS-NFR-SEC-06
Git-репозиторій не повинен містити секретів розгортання. Джерело: NFR-10.

#### SRS-NFR-OPS-02
Експлуатаційна процедура повинна створювати копії кожної з трьох PostgreSQL-БД щонайменше раз на 24 год. Джерело: NFR-10.

#### SRS-NFR-OPS-03
Процедура відновлення повинна забезпечувати цільовий RPO ≤24 год, перевірений контрольними даними резервної копії. Джерело: NFR-10.

#### SRS-NFR-OPS-04
Процедура відновлення трьох PostgreSQL-БД повинна забезпечувати цільовий RTO ≤4 год, виміряний під час restore. Джерело: NFR-10.

Доповнення інфраструктурних обмежень за ЛР №5:

#### SRS-NFR-SEC-04
Gateway повинен обмежувати check/launch до 30 запитів/хв на IP з burst 5 та повертати 429 при перевищенні.

#### SRS-NFR-SEC-07
Gateway повинен обмежувати auth до 60 запитів/хв на IP з burst 20 та повертати 429 при перевищенні.

#### SRS-NFR-OBS-01
Система повинна повертати визначений контракт помилок: 422 для DTO, 401/403 для автентифікації/доступу та код доменної відмови для бізнес-помилок.

#### SRS-NFR-SEC-08
Відповідь на невідому внутрішню помилку не повинна розкривати stack trace клієнту.

#### SRS-NFR-REL-03
HTTP-виклики залежностей повинні мати кінцеві connect/read/write/pool timeouts; цільовий ліміт мережевої неактивності кожної фази — 5 с. Це не сумарний SLA виклику. Джерело: NFR-08; перевіряються також повільний потік даних і недоступний зовнішній провайдер.

#### SRS-NFR-REL-04
Redis connect і socket operation повинні мати timeout 0.5 с без автоматичних повторів; помилка повинна передаватися в контрольований fallback або відмову. Джерело: NFR-08.

#### SRS-NFR-REL-05
Контур VIP-завантаження повинен обмежувати весь запит, включно з connect/publish/reply, загальним deadline 30 с; невиконаний запит завершується контрольованою помилкою. Сам reply-timeout REL-01 не доводить виконання цієї вимоги. Джерело: NFR-08. Це цільове уточнення приймання, а не заява про наявний загальний таймер.

## 4. Verification Criteria — критерії верифікації

Це план перевірки; запуск навантажувальних, безпекових і restore-тестів не заявляється. Перед протоколом приймання фіксуються commit, конфігурація, тестові дані, версії інструментів і час виконання.

- **VC-01:** FUN-01/02 — Playwright: гостьові сторінки, інструкції, зовнішні переходи й успішне Free-завантаження; перевірка відсутності виклику VIP-збірки.
- **VC-02:** FUN-03/04/05/20/21/22, SEC-02/05 — pytest + httpx з контрольованими відповідями провайдерів: валідний/пошкоджений підпис, прострочення, зв’язування ідентичностей, logout і повтор старого refresh. Окремо — ручний end-to-end вхід у sandbox-акаунтах провайдерів.
- **VC-03:** FUN-06/07/08/09/24, CONS-01 — pytest + PostgreSQL: формат ключа, переходи станів, owner/history, заблокований і прострочений ключ; 20 конкурентних активацій для різних власників.
- **VC-04:** FUN-10/11, CONS-02, SEC-03 — pytest + PostgreSQL: гранична квота пристроїв, паралельне додавання і скидання, 100 чужих ID. SQLite не замінює перевірки транзакцій PostgreSQL.
- **VC-05:** FUN-12/13, PERF-04, REL-01/02/05, FILE-01/02/03 — pytest + RabbitMQ і тестова Distribution-збірка: 20 штатних запитів, відсутній consumer, таймаут, відмова ліцензії, повторне завантаження та sweep; вимірювання p95 окремо від API-профілів.
- **VC-06:** FUN-14/15/17, PRIV-01/02 — pytest/httpx: валідні/некоректні події, контрольні SQL-агрегати, 100 публічних відповідей і перевірка журналів на секрети.
- **VC-07:** FUN-16/18/19/23 — pytest з тестовими Stars-подіями, ролями та моками ботів: облік підтвердженої оплати, відхилення неадміністратора, команди завершення підписки.
- **VC-08:** PERF-01/02/03/05 — k6 constant-arrival-rate; звіт http_req_duration p(95), http_req_failed і dropped_iterations. Налаштовані per-IP limits враховуються: статистика й внутрішній профіль не підміняються навантаженням check/launch з одного IP.
- **VC-09:** CACHE-01/02/03/04, REL-04 — pytest + Redis: контроль часу fresh/stale, 20 конкурентів, облік loader-викликів, cold 503/Retry-After та відмова Redis.
- **VC-10:** SEC-01/04/07 — curl/openssl s_client: заборонені версії TLS; серія запитів через gateway для меж частоти й 429. Trivy config/image scan доповнює, але не доводить авторизацію.
- **VC-11:** OPS-01/02/03/04, SEC-06 — Docker Compose config/up, Trivy secret/config scan; pg_dump/pg_restore трьох БД, контрольні запити й виміряний час відновлення. Копії — поза тим самим volume/хостом.
- **VC-12:** OBS-01, SEC-08 — pytest/httpx: 422/401/403, контрольовані доменні та невідомі помилки; перевірка відсутності stack trace і секретів. Статичний аналіз Ruff/Bandit є додатковим контролем, а не заміною тестів поведінки.

- **VC-13:** REL-03/05 — pytest/httpx mock transport, Toxiproxy або контрольований proxy: connect/read/write/pool timeout, повільна відповідь провайдера, broker недоступний до publish, відсутній consumer; вимірюється завершення всього VIP-запиту до 30 с. Ліміт 5 с не підміняє загальний deadline.

## 5. Glossary — глосарій

- **Micro-SaaS:** вузькоспеціалізована платформа для супроводу одного продукту; не синонім мікросервісів.
- **Freemium:** модель з безкоштовними можливостями продукту та окремим платним доступом.
- **Ліцензія:** запис права користувача на платний доступ зі станом, строком і правилами пристроїв.
- **HWID:** ідентифікатор пристрою; не доказ унікальності фізичної особи.
- **JWT:** підписаний токен із claims; перевірка підпису не замінює перевірки власника ресурсу.
- **p95 Latency:** час, якого не перевищують 95% спостережень у визначеному тестовому профілі.
- **RPC через AMQP:** запит і відповідь через брокер з correlation ID та reply queue; не гарантія exactly-once.

## Статус проєктних обмежень

Вимоги описують приймання цільової системи. Зокрема загальний deadline REL-05, інверсія залежностей на C4 Component і повне маскування всіх технічних журналів потребують перевірки реалізації. Проєктні інтерфейси не подаються як уже створені класи.
