# ADR-001: RabbitMQ для команд ботам і RPC підготовки VIP-файлів

**Status:** Approved — проєктне рішення в межах ЛР №5; не означає погодження викладачем або завершення перевірок.

**Дата:** 28.10.2026 · **Автор:** Маргер Богдан Євгенович.

## Context

License Service приймає рішення про платний доступ, Distribution Service виконує окрему збірку файлу, а боти адаптують команди до Telegram/Discord. Потрібні адресована доставка завдання, відповідь конкретному запиту та маршрутизація команд двом типам ботів. Вимоги: [FUN-12](../srs.md#srs-fun-12), [FUN-19](../srs.md#srs-fun-19), [REL-01](../srs.md#srs-nfr-rel-01) і [REL-02](../srs.md#srs-nfr-rel-02). Сценарій збірки має окремий p95 ≤30 с; це ціль, яку потрібно перевірити. Replay довготривалої історії подій і багатокластерний streaming до вимог не входять.

## Alternatives

1. **RabbitMQ / AMQP.** Черга завдань, reply queue та correlation ID відповідають запиту на конкретну збірку. Topic exchange придатний для адресації telegram.# і discord.#. Потрібен окремий broker, контроль acknowledgement, таймаутів і повторної доставки.
2. **Прямий REST / HTTP.** Для одного виконавця дає простіший експлуатаційний контур і може виконати той самий функціонал. Потребує власного контролю повторів і доступності виконавця; немає спільної брокерної маршрутизації команд. Не відкидається як універсально повільний або ненадійний.
3. **Apache Kafka.** Орієнтована на журнал подій, незалежні consumer groups і повторне читання. Request/reply потребує додаткових домовленостей щодо topics, correlation і retention. Її властивості replay тут не є вимогою; без порівняльних вимірювань не заявляється програш Kafka за Latency або споживанням ресурсів.

## Decision

Обрано RabbitMQ: чергу file_generation_queue для підготовки файлу, окрему callback-чергу з correlation ID для відповіді та topic exchange для команд ботам. Власні HTTP API зберігаються для профілів, перевірки ліцензій та операцій кабінету. [C4 Container](../2_design.md#diagram-level2) показує ці два контури.

RPC через брокер не перетворює HTTP-сценарій на фоновий job: користувач очікує URL або контрольовану помилку. Для очікування відповіді встановлено 30 с; connect/publish і зовнішній HTTP timeout повинні окремо контролюватися в прийманні. Результат не можна називати exactly-once або гарантією доставки за будь-якої відмови.

## Consequences

### Позитивні

- Distribution і боти мають окремі контракти виконання; їхні процеси не входять до процесу HTTP-сервісу ліцензування.
- Correlation ID дозволяє зіставляти reply з конкретним запитом; routing keys відокремлюють команди Telegram і Discord.
- Транспортні сценарії можна відтворити в Compose та перевірити fault-injection тестами.

### Негативні та ризики

- Додаються витрати пам’яті, диска, моніторингу й оновлення broker; FinOps-оцінка потребує фактичних вимірювань, які ще не отримано.
- Один broker на одному хості не забезпечує High Availability. Відмова може зірвати збірку або доставку бот-команди.
- Повторна доставка може породити повторну збірку або команду. Correlation ID не є дедуплікацією чи транзакцією між PostgreSQL і RabbitMQ.
- Коміт завершення підписки й публікація команди не є спільною атомарною транзакцією; transactional outbox не заявлено. Потрібні контроль помилок і звіряння привілеїв, а їх реалізація перевіряється окремо.
- Таймаут клієнта не доводить скасування вже запущеної збірки. Покинуті файли повинні прибиратися згідно з [FILE-01](../srs.md#srs-nfr-file-01).
- Контракти payload, reply і routing keys створюють витрати сумісності. Інтеграційні тести потребують доступних RabbitMQ і Distribution, а не лише моків HTTP.

### Критерій перегляду

Рішення переглядається, якщо з’явиться вимога довготривалого replay, незалежних потокових споживачів, HA або якщо вимірювання не підтвердять бюджет збірки. Заміна технології оформлюється новим ADR із посиланням на цей запис.
